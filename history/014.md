# History Entry 014: Hardware Migration to GCP for Native bfloat16 Support

## 1. Context
During the execution of the fine-tuning pipeline on Google Colab's free tier (NVIDIA T4 GPU), the `gemma-4-e2b-enhanced` configuration encountered a catastrophic `torch.OutOfMemoryError` during the initial loss calculation step. 

Investigation of the logs revealed the root cause was a combination of hardware architecture limitations and framework fallbacks:
1. **Massive Vocabulary Size:** Gemma 4 uses a vocabulary of 262,144 tokens. At a sequence length of 2048, the materialized logits tensor is exceptionally large.
2. **Turing Architecture Limitations:** The T4 GPU (sm_75) lacks native support for `bfloat16`. 
3. **Unsloth Fallback:** Because Gemma 4 experiences numerical instability in `float16`, Unsloth caught this limitation and silently upcasted the compute dtype to `float32`. This caused the optimized Triton cross-entropy kernel to fail to attach, falling back to naive PyTorch `F.cross_entropy`. 
4. **Memory Spike:** The fallback caused the logits gradient tensor footprint to double (from ~1GB to ~2.14GB), instantly breaching the remaining ~1.8GB of free VRAM on the 16GB T4.

**Resolution:** The project has officially pivoted its hardware strategy. We are migrating off Google Colab and onto dedicated Google Cloud Platform (GCP) Deep Learning VMs utilizing NVIDIA L4 (Ada) or A100 (Ampere) GPUs. These architectures natively support `bfloat16`, allowing Unsloth's optimized loss kernels to function correctly and eliminating the FP32 memory spike.

## 2. Modifications
* **Removed:** `google-colab.ipynb` and `scripts/colab_bootstrap.sh` as the pipeline is no longer constrained to browser-based Jupyter environments.
* **Added:** `SETUP.md` - A comprehensive guide for provisioning GCP Compute Engine instances, requesting GPU quotas, and running the pipeline headlessly using `tmux`.
* **Modified:** `configs/gemma-4-e2b.yaml`
  * Increased `per_device_train_batch_size` from `1` to `4` to fully utilize the 24GB VRAM available on the L4 GPU.
  * Decreased `gradient_accumulation_steps` from `16` to `4` to maintain an effective batch size of 16.
* **Modified:** `configs/gemma-4-e4b.yaml`
  * Increased `per_device_train_batch_size` from `1` to `2`.
  * Decreased `gradient_accumulation_steps` from `16` to `8`.
