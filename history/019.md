# Log 019: Add Granite 4.2 3B as Dense-Transformer Control Model

**Context:**
Gemma 4 E2B (per-layer embeddings, sliding/full attention) and Qwen3.5-2B (hybrid linear/full
attention) are both architecturally unusual. Without a conventional baseline, an underperforming
result cannot be attributed to model family versus architecture, and both carry GGUF-export risk
in llama.cpp. Granite was in the original proposal (Granite 4.1) and was dropped only for
hardware reasons; `ibm-granite/granite-4.2-3b` restores it as a control at ~3B parameters, which
fits a T4 in 4-bit QLoRA. It is run in the enhanced-schema configuration only, keeping the
schema-filtering ablation on the two primary models.

**Modifications:**
- **`.gitmodules`:** added `data/granite-4.2-3b` (`ignore = dirty`), registered with
  `GIT_LFS_SKIP_SMUDGE=1` so weights come from `download_data.sh`, not git LFS.
- **`download_data.sh`:** new `granite` target; included in `all`.
- **`src/config.py`:** `granite-4.2-3b` registry entry (family `granite`, SDPA, system role
  supported, `thinking`/`enable_thinking` set to False defensively since the repo ships a
  reasoning parser); aliases `granite`, `granite-3b`, `granite3b`; `<|end_of_text|>` added to
  generation stop strings.
- **`src/env.py`:** Granite added to the local model checks; VRAM warning text updated.
- **`data/0-sample/data.py`:** extracts Granite config, tokenizer config and chat template.
- **`configs/granite-4.2-3b.yaml`:** hyperparameters identical to the Gemma config
  (batch 1 x accumulation 16, lr 2e-4, r=16); Unsloth disabled so all models share the
  target-only loss path.
