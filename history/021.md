# Log 021: Exact-Path LoRA Targets (Gemma 4 Towers) & Native-bf16 Detection

**Context:**
The first set-and-go run of gemma-4-e2b-enhanced failed while attaching LoRA:
PEFT rejected `Gemma4ClippableLinear` in the vision tower. The same run reported
`Compute Dtype: torch.bfloat16` on a T4. The previous doctor run in this environment
(different transformers patch release) had reported "bfloat16: Not Supported".

**Modifications:**
- **`src/training/model_loader.py`:**
  - LoRA target discovery now returns exact module paths to PEFT. Previously it returned leaf
    names (`q_proj`, …), and PEFT matches those anywhere in the model. That included Gemma 4's
    vision/audio towers, whose projections are `Gemma4ClippableLinear` wrappers PEFT does not
    support. The towers were filtered out of the scan, but not out of PEFT's matching.
  - Run metadata records a compact summary (module count + leaf names) instead of the full list.
  - The Unsloth path still receives leaf names.
  - `select_dtype()` uses bf16 only on compute capability >= 8.0. Recent PyTorch reports
    `is_bf16_supported() == True` on Turing via emulation, which would have trained the T4 in
    emulated bf16 instead of the intended fp16 + GradScaler path.
  - `_dtype_kwarg()` picks `dtype` vs `torch_dtype` by transformers version (>= 4.56). The
    signature probe failed on v5 because `from_pretrained` only exposes `**kwargs`, which caused
    the `torch_dtype is deprecated` warning.
- **`src/env.py`:** doctor uses the same capability check and shows "Emulated only (not used)"
  when PyTorch claims emulated bf16.
