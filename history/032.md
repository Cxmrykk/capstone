# Log 032: Edge (CPU) Evaluation Notebook and Supplementary Analyses

**Context:**
`final-eval-kaggle` (r030) produced the GPU thesis numbers, but its GGUF CPU benchmark was disabled by default.
It also never measured several things the edge-deployment question needs:
- an export rebuilt from the verified final adapters;
- CPU throughput and its thread scaling;
- memory footprint;
- per-query prefill/decode latency;
- tokenizer parity between GGUF and training;
- CPU accuracy paired with the GPU result on identical rows.

The final-eval README also claimed that its GGUF rows were "a smaller subset" of the evaluation rows. That only held because of how `random.sample` happens to work, not by design. Several analyses that the r030 tables suggest were also missing:
- `neo4jLabs_functional_cypher` (159/500 rows, EM 0.93-0.98) inflates the text metrics;
- only about 213 of 500 rows are judged for execution accuracy;
- the exact-match filter's coverage of gold-query elements was never measured;
- matches on empty gold results were not separated from real matches.

**Modifications:**
- **Added `notebooks/edge-eval-kaggle/`** (15 chunks + `notebook.json`, Kaggle CPU session, accelerator none).
  No changes to `src/`, configs or scripts. Build with `python notebooks/build.py edge-eval-kaggle`.
  - **Rows:** re-derives the 500 reference rows with `subsample(..., 500, 3407)` and checks them against every r030
    job. It then draws an explicit seeded subset (`EDGE_LIMIT`, default 100, `random` or `stratified` by database access)
    whose hash (`edge_ids_sha`) gates reuse.
  - **llama.cpp:** a CPU build (`GGML_NATIVE=ON`, `LLAMA_CURL=OFF`) of `llama-server`, `llama-quantize` and
    `llama-bench`, built in the notebook. The build script's `git pull` would fail on a detached pinned commit.
    `LLAMA_CPP_REF` pins the commit; when blank, the first session records its commit at
    `edge-eval/<suffix>/llama_cpp_commit.txt` and later sessions build it.
  - Only `gguf-py` + sentencepiece/protobuf are installed for the converter. The full converter requirements pin older
    transformers releases, so the `transformers>=5.5.0` floor is re-asserted afterwards.
  - **Export:** `app.py export merge --dtype float32` (exact LoRA merge) runs on the CPU, then
    `app.py export gguf --quant F16`, then `llama-quantize` per needed quantisation. The export refuses to continue
    unless the merge log contains `Adapter verified` (history/027.md). It records `model_class`, sizes, SHA-256 and
    timings in `edge-eval/<tag>/exports/<run>.json`. Only runs with unfinished work in the session are exported.
  - **Throughput and footprint:** one run per model, because speed does not depend on the adapter.
    - `llama-bench -o json` ppN/tgN: a thread sweep for `THREAD_SWEEP_QUANTS`, the full thread count for the others.
    - `llama-server --no-mmap` load time, RSS after load, VmHWM and first request per quantisation.
    - With `SERVER_THREADS = 'auto'`, the thread count minimises median-prompt prefill plus typical-generation time.
  - **Accuracy jobs:**
    - Prompts are built with the same calls as `app.py predict` (`apply_schema_mode`, `fit_prompt_to_budget`,
      `prompt_reserve_tokens`, `strip_leading_bos`).
    - Requests go directly to llama-server's `/completion` (greedy, `top_k` 1) so that `timings`, `tokens_evaluated`
      and the stop type are kept; `LlamaCppBackend` discards these.
    - Stops on EOS only by default, matching HF `generate`.
    - Writes predict-compatible rows plus `edge_*` fields and is scored by `app.py evaluate --execute --validate-syntax`.
    - Priorities: Q4_K_M for every run, then cross-schema, then Q8_0 for enhanced runs. Jobs start only if their
      estimate fits the session budget.
    - Job IDs are `<reference_job_id>__gguf_<quant>_cpu`, so every job pairs with its r030 GPU job.
  - **Aggregation:**
    - Wilson/bootstrap CIs; GPU metrics restricted to the same rows.
    - Paired McNemar/bootstrap tests with Holm correction, and TOST for GPU-vs-CPU equivalence.
    - Families: edge_vs_gpu, quant_fidelity, schema filtering/inference/training effects on the CPU, and model
      comparison.
    - Identical-prediction shares, a schema latency/accuracy trade-off table, and tokenizer parity.
    - Integrity checks: single CPU model, llama.cpp commit and code commit; adapter verification; request errors;
      `stopped_limit`; connection failures; expected jobs.
  - **Supplementary analyses (GPU references and CPU jobs):**
    - subset metrics (without `functional_cypher`, with/without database);
    - exact-match filter coverage of gold labels, relationship types and properties, and execution accuracy split by
      coverage;
    - schema hallucination (elements absent from the full schema or from the prompt schema);
    - breakdown of execution results (empty-gold matches, row-count mismatch);
    - oracle/majority agreement across models;
    - sample composition.
  - **Outputs:** `artifacts/thesis-edge/<edge_tag>/` (tables CSV and `.tex`, `edge_predictions_long`, `results.json`,
    `manifest.json` with `lscpu`, README, 8 figures). These are copied to `/kaggle/working` and uploaded to
    `edge-eval/<edge_tag>/thesis/<session>/`.
